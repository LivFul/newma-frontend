## Contract (shared with the frontend/backend P5a plan — identical in both files)

All `/v1/*` requests: `Authorization: Bearer <BFF_SERVICE_TOKEN>` and `X-Demo-Session: <session_id>`. Error envelope `{code, message, details}`. Every route below is tenant-scoped (`tenant_scope`) and persona-checked with `require_persona(...)`; a persona outside the allowed set gets **403 `persona_forbidden`** with `details: {persona, allowed: string[]}`. "any" means all eight personas. Lists use `{items: T[]}` (newest first, at most 100). Writes marked (idem) take `idempotency_key` (`^[A-Za-z0-9._:-]{1,128}$`); a replay returns **200** with the original body and header `Idempotent-Replayed: true`; same key with a different body → 409 `idempotency_conflict`. Writes marked (event) append a signed provenance event and return its id in the resource (`event_id`). Money is an integer in **demo credits** (`*_demo_credits`, never a currency, never a float); rule shares are integer **basis points** and are always labelled "Illustrative".

Shared vocabularies (exact):

- `SettlementState` = the WP §3.6 states already in `settlement/state_machine.py`: `submitted reviewed approved disputed receipts_reconciled distribution_authorized funded paid audited paused` (`paused` is never produced by P5a).
- `LicenseState` = `requested credential_check approved denied`. `CredentialStatus` = `not_requested verified failed`. `LicenseAction` = `credential_check decide`.
- `SettlementAction` (what the state allows next, persona-agnostic) = `record_receipt review dispute resolve evidence_approval reconcile approve_distribution distribute audit`.
- `ReceiptStatus` = `recorded duplicate disputed` (existing). `LedgerKind` = `beneficiary reserve residual`. `BenefitStatus` = `planned scheduled delivered`. `AnchorStatus` = `not_requested pending anchored`. `LicensePurpose` = `research commercial` (a subset of P3 `Purpose`).
- Provenance for the new entities: `entity_type` is `license` or `settlement` in the event log and in `{entity_type: string}` timelines; the P3 `EntityType` enum and `GET /v1/provenance/{entity_type}/{entity_id}` are **unchanged** (A-P5A-10). Manifests are read and verified through the existing `GET /v1/provenance/events/{event_id}/manifest` and `POST /v1/provenance/verify`.
- Labels: `"Optional, simulated"` (credential check, anchoring), `"Demo signature, not production key"` (every signed object), `"Illustrative"` (rules, shares, calculation), `"Synthetic"` badge, unit text `"demo credits"`.

Assumptions (copy into `PROGRESS.md` when the task that relies on each one lands; ids are shared by both repos' P5a plans; frontend-only ones are `A-P5A-Fnn` in the frontend plan):

- `[Agent assumption A-P5A-01]` **Source gap.** The planning session could not read the sprint plan, Technology Architecture, PRD, white paper or Implementation Plan (OneDrive placeholders timed out on read). Scope comes from the controller brief for TRACK A (sprint plan §3.2 W7 and §5 D-17 as summarised there), the P2/P3 plans, the invariant block and the existing `settlement/state_machine.py` docstring (which already cites WP §3.6). Task 0 of the backend plan re-reads the named sections and records any conflict here; until then no citation below is claimed beyond what those repo documents already carry.
- `[Agent assumption A-P5A-02]` **State machines.** The settlement machine is used unchanged. Mapping: `POST /v1/settlements` = evidence submitted (`submitted`); `review`; `evidence-approval` = `approve`; `dispute`/`resolve`; `reconcile` = `reconcile_receipts`; the second distinct approval = `authorize_distribution`; `distribution` = `fund` then `pay` in one transaction; `audit` = `audit` plus the signed commitment. `pause`/`resume` stay in the machine and are not exposed. The license gets a small machine `LICENSE_MACHINE` (`requested`, `credential_check`, `approved`, `denied`; events `start_check approve deny`): `credential_check` means "check completed, awaiting a decision"; the check is optional (`requested + approve` is legal); a failed check can only be denied.
- `[Agent assumption A-P5A-03]` **Receipts.** Rows are immutable except `status` and `dispute_reason` (column-level `UPDATE` grant). A duplicate (same `agreement_id` + `external_ref` as a live `recorded` or `disputed` row) is stored as status `duplicate` with `duplicate_of`, answered 409 `receipt_duplicate`, and excluded from every total; uniqueness is a partial unique index over non-duplicate rows, so concurrent submissions end with one live row. Disputes are raised only at `reviewed` (the only machine edge into `disputed`); receipts can be recorded in `submitted reviewed approved` and are frozen from `receipts_reconciled`. Only `reinstate` exists as a dispute outcome (no forfeiture rule is invented).

## Review Focus

1. **Rounding and residual conservation on screen** — the calculation table renders the backend's integer lines in the served order, labels the `residual` line "Rounding residual (carried to the reserve pool)", never shows a percentage, and a pure `checkConservation(calculation)` sums the displayed integers and renders "Conserved: <n> demo credits" or a visible `role="alert"` mismatch. Unit tests with the awkward-amount fixture (7 demo credits) and a deliberately broken fixture; no `Number` arithmetic other than integer addition, no `toFixed`, no division.
2. **Double approval** — the approvals panel lists each approver persona with time and rationale; the approve dialog generates one idempotency key when it opens and reuses it for every submit; the submit button is `aria-busy` while in flight (double click → one approval, the second a 200 replay rendering the same approval); a persona that already approved sees the control disabled with the reason, and a forced second POST renders 409 `approver_already_approved`; the first approval shows "1 of 2 approvals — a different approver persona must also approve" and never "authorised".
3. **Duplicate receipt from the UI** — the record-receipt form keeps one stable key per submission; the 409 `receipt_duplicate` refusal renders "Duplicate receipt rejected — not counted" with the original row highlighted, the refreshed table shows the stored `duplicate` row struck through with its reason, and the totals row does not change. A retry after a timeout is a replay (no second row).
4. **Disputed receipt payout leak** — while the settlement is `disputed` or any receipt is `disputed`, the page offers no reconcile, approve or distribute control (controls come from `next_actions` intersected with the persona hint), the calculation shows the disputed amount as "held — not payable" outside the distributable total, the ledger panel reads "No payout: nothing has been posted", and a forced POST to `/reconcile` and `/distribution` is asserted to be refused (409) in Playwright.
5. **Anchoring outage not blocking other work** — with the outage on, the settlement is `audited` and signed immediately, the anchor panel shows "Pending (simulated chain outage) — Optional, simulated", every other control stays usable, and Playwright starts a simulated screening job in the same session and sees it reach a terminal state while the anchor is still pending; switching the outage off ends in "Anchored" with the receipt reference; polling stops on unmount.
